# references/FRONTEND_CONTRACT.md

`whatsales-frontend` (React/Vite, deployed on Vercel — see
`.ai/references/RAILWAY_ENV.md`) is a **separate repo**, not covered by
this `.ai/` knowledge base directly. This doc exists so an AI working
across both repos (or asked to change a dashboard-facing response shape in
*this* repo) knows what the frontend actually expects, without having to
open the other repo to find out. It is the one place in this knowledge
base that describes the other repo's expectations — everything else here
describes only this backend.

**If you don't have access to `whatsales-frontend` in this session, treat
this file as the best available substitute — but flag explicitly that you
haven't verified it against the frontend's actual code**, since (unlike
every other `.ai/` doc in this project) it wasn't generated by reading the
other repo directly; it's derived from this backend's controller/route
contracts in `.ai/controllers/ADMIN_APIS.md`.

## Where the contract actually lives

The authoritative shape of every response is whatever
`controllers/dashboardController.js`, `controllers/tenantController.js`,
and `controllers/whatsappOnboardingController.js` actually return — see
`.ai/controllers/ADMIN_APIS.md` for the full route table. This file is a
convenience index on top of that, not a second source of truth. If the two
ever disagree, the controller code wins (same rule as everywhere else in
this knowledge base — see `.ai/README.md`'s opening paragraph).

## Auth the frontend must send

Every `/dashboard/:tenantId/*` and `/business/:tenantId/*` request needs an
`x-api-key` header carrying the tenant's own API key (see
`.ai/references/MULTI_TENANT_SECURITY.md`). The frontend has no separate
session/cookie auth layer of its own as far as this backend is concerned —
whatever the frontend does with login state (`adminUserController.js`
handles dashboard-admin-user accounts) still resolves down to this one
header on every API call. If you change how `req.tenantId` is derived on
the backend, the frontend's stored-credential handling is the thing that
breaks silently on the other side.

## Polling cadence the backend is tuned for

`overviewLimiter` (30/min) and the analytics/conversation endpoints are
rate-limited assuming the frontend polls `GET /overview` roughly every
120s and `GET /sessions/:tenantId`-style endpoints roughly every 60s (see
`.ai/references/ANALYTICS_AND_UTILS.md`'s rate-limit table). **If the
frontend's polling interval ever changes, the corresponding limiter's
`maxPerMinute` needs to change with it** — a tighter frontend poll against
an unchanged limiter will start throwing 429s in a way that looks like a
backend regression but is actually a frontend/backend cadence mismatch.

## Response shape expectations by endpoint group

These are the fields the frontend is understood to render directly (not
just pass through) — treat removing or renaming any of them as a breaking
change requiring a coordinated frontend PR, not a same-repo refactor:

| Endpoint | Frontend renders | Backend source |
|---|---|---|
| `GET /overview` | Order/booking counts, revenue snapshot, active-conversation count | `getDashboardOverview()` |
| `GET /orders` | `status`, `items[]`/`item`, `totalPrice`, `paymentStatus`, `shortId`, per-status timestamps | `Order` schema — see `.ai/business/DATA_MODELS.md` |
| `PATCH /orders/:orderId/status` | Expects the updated order back with the new `status` reflected, and expects the customer to have already been notified server-side (see the `[FIX-6a]` note in `.ai/controllers/ADMIN_APIS.md`) — the frontend does **not** send its own customer notification | `updateOrderStatus()` |
| `GET /bookings` | `status`, `date`/`time`, `service`, `staff`, `shortId` | `Booking` schema |
| `GET /analytics`, `GET /analytics/timeseries` | Chart data keyed by the 4 `Analytics.type` values (`ORDER`/`BOOKING`/`FAILED`/`REVENUE`) — see `.ai/references/ANALYTICS_AND_UTILS.md`'s `EVENT` → `type` mapping table before adding a 5th bucket, since the frontend's chart legend is understood to be hardcoded to exactly these 4 | `analyticsService.js` |
| `GET /conversations`, `PATCH /conversations/:phone/human` | `humanMode` boolean toggle — the frontend's toggle switch reflects this field directly | `getConversations()` / `setHumanMode()` |
| `GET /menu`, `/menu*` mutations | `menuItems[]` shape including `variants` — a frontend that was built/tested before `variants` was declared in the schema (see Rule 1 in `.ai/README.md`) may have its own stale assumptions about this field; verify both sides agree if variant-related bugs appear | `BusinessConfig.menuItems` |
| `GET /settings`, `PATCH /settings` | `BusinessConfig.settings.*` — notably `estimatedDeliveryMinutes`, used both by the dashboard display and by `postFlowHandler`'s `ORDER_CONFIRMED` ETA message (`.ai/flows/POST_FLOW.md`) | `BusinessConfig.settings` |
| `POST /api/whatsapp/request`, `GET /api/whatsapp/request/status` | Tenant-facing onboarding form + status poll | `whatsappOnboardingController.js` |

## What NOT to assume

- Don't assume the frontend has its own validation mirroring this
  backend's Mongoose schema — assume it doesn't, and that any new
  required field needs a backend-side default or the frontend can send a
  request that's missing it entirely.
- Don't assume a backend response-shape rename is a "just update both
  repos" one-PR job you can do solo from this repo — the two repos deploy
  independently (Railway vs. Vercel), so a breaking rename needs either a
  backward-compatible transition period (old + new field both present for
  one release) or explicit coordination on deploy order.
- Don't assume this file is exhaustive. It covers the fields known to be
  frontend-load-bearing as of this writing; if you're about to change a
  response shape not listed here, the safe default is still to treat it as
  potentially frontend-facing and check before removing/renaming a field,
  not to assume silence here means "safe to change."
